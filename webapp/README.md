# TraceEvo 双图审计溯源 Web 系统

面向医学多智能体协同推理的双图审计溯源与可信经验固化。

系统的核心不是聊天界面，而是让**医学因果推理图**与**协作执行溯源图**如何随
多智能体协作逐步构建、更新、审计、最终固化为经验变得可见。

一句话概括它要证明的事：

> 医学推理图只能看到它支持什么；执行溯源图才能回答这些支持是从哪里来的。

## 快速开始

```bash
./webapp/run.sh              # 开发模式：后端 8000 + 前端 5173
./webapp/run.sh --build      # 演示模式：只起后端 8000，静态托管构建产物
./webapp/run.sh --help       # 全部选项

TRACEEVO_PORT=8001 ./webapp/run.sh   # 8000 被别的服务占用时换端口
```

换端口不需要改任何文件：`run.sh` 会把反代目标通过 `TRACEEVO_API` 传给 Vite。
（少了这一步，前端会静默地去连 8000 上那个**别的**服务 —— 表现是接口返回
形状不对的 JSON，而不是「连不上」，排查起来会绕远路。）

打开 <http://127.0.0.1:5173/> 进入系统总览，或直接进
<http://127.0.0.1:5173/workbench/case-ankle>（演示病例，见下）。

**演示模式不需要任何模型 API** —— 它只读已落盘的 artifact。这正是需求中的
「模拟数据模式」，而读的是**产物**而不是编造的响应：封存运行、真实分析、
手写展示轨迹三种数据源交出同一个协议，前端不分辨它们（`case-ankle` 是
唯一一处数据本身是手写的，见下）。

### 三个知识库目录

系统总览中的「三个知识库」入口打开 `/knowledge-bases`。页面首先展示从本地
Patient Evidence、Medical Knowledge 和 Experience 数据源整理的中文短摘要，并按
字段结构呈现；患者证据样例不显示任务 ID 和记录 ID。每个库的记录数及内容分布
放在样例之后。数据由 `GET /api/knowledge-bases` 提供，接口对 SQLite 使用只读
连接，不会初始化或修改 Qdrant collection。

### 演示病例是怎么来的

演示病例有两份，**性质完全不同**，界面上必须能分开：

| | `case-ankle`（默认演示） | `case-0`（真实分析） |
|---|---|---|
| 数据 | **手写**（`webapp/showcase/ankle.json`） | 真跑出来的产物 |
| 终图 | 10 节点 / 11 边，7 步（含反证、回溯、继续深挖和报告），两级假设 | 8 节点 / 14 边，单级 |
| 节点信息 | 输入与首轮假设沿用参考图；后续证据和替代假设按展示轨迹编排；不含 X 光节点 | 来自实际运行产物 |
| 审计产物 | **不适用**：展示绑定仅用于回放；没有 P0–P3 判定、匹配度、哈希、重放结论或真实模型账本 | 齐全（P0 直接有据 4 / P2 合法推导 4，完整性与重放均通过） |
| `kind` | `showcase` | `live` |

#### 对齐的参考前端

`case-ankle` 复用桌面项目独立前端演示中的输入、L1 假设与分数：
`医疗溯因智能体/demo/causal_graph_demo.html`，由同目录的
`demo/make_demo.py` 生成。之后用一条专门编排的反证与回溯轨迹展示推理如何修正：
先深挖 L1 最高分的软组织损伤（0.55），再由 MRI 反驳 L2 的 ATFL 完全断裂；中央智能体
回溯后重新选择仍然最高分的 L1 节点，继续深挖并得到 ATFL 部分撕裂。将纯操作步骤并入
相邻的证据/回溯步骤后，工作台共 7 步：

- Step 0：只显示症状与初始查体证据，不显示假设或因果边；
- Step 1：生成三个 L1 假设，对应参考页第一帧；
- Step 2：中央智能体选择当前最高分的软组织损伤，细化为 ATFL 完全断裂（0.92）和肌肉挫伤（0.08）；
- Step 3：中央智能体继续深挖 L2 最高分候选并调用放射科专家；MRI 初读反驳 ATFL 完全断裂，置信度由 0.92 降至 0.10；
- Step 4：执行 Backtrack，焦点从 node-8（L2）切回 node-6（L1，0.55），并从该最高分节点继续深挖；
- Step 5：放射科专家复核 MRI，支持 ATFL 部分撕裂，并形成替代 L2 假设；
- Step 6：生成最终报告。因本轨迹不含 X 光，不宣称已影像排除骨折。

参考页的 `make_demo.py` 复用了节点字典，生成 HTML 时后续分数也改写了较早帧：首帧
实际显示 L1 为 0.15 / 0.55 / 0.30，L2 为 0.92 / 0.08。TraceEvo 保留这些分数，
但不包含参考中的 X 光节点与相关边，因为当前展示改为直接深挖最高分 frontier。

桌面项目的 GoS 交互故事 `gos_repo/viz/stories.py` 是另一条 7 步轨迹，含知识会诊；
它不是这次要对齐的独立前端演示。

用下面的命令逐帧检查：

```bash
../医疗溯因智能体/gos_repo/.venv/bin/python webapp/showcase/check_alignment.py
# ✓ case-ankle 的输入、L1 与首轮 L2 和参考数据一致；后续 MRI 反驳、回溯、重新深挖与报告路径通过校验：工作台 7 步 · 终图 10 节点 · 11 边
```

检查器直接读取参考 HTML 中实际展示的 `graphData`，对照输入、L1 与第一轮 L2 状态；
后续专门校验“新证据反驳 L2 → Backtrack 到 L1 最高分节点 → 继续深挖 → 最终报告”的
图状态、事件因果引用与 API 输出。

#### 为什么默认演示是手写的

`case-ankle` 是手写 showcase：复用参考图的输入、首轮 L1/L2 节点与分数，之后编排
MRI 反证、回溯到 L1 最高分节点、替代细化和最终报告等过程事件；它不是中央智能体的
真实运行，不产生审计判定。后续 MRI 结果是为了展示该轨迹而编写，不应误读为原参考页
中的真实检查结论。

`webapp/showcase/ankle.json` 由 `build_ankle_showcase.py` 生成。展示绑定服务于节点回放；
来源审计、账本、哈希链与重放结论均不适用。

#### 边界怎么焊死的

`kind = "showcase"` 一路从数据源传到响应，三个地方据此改变行为：

* `services/audit.py` **不去跑**审计 —— 跑了会从手写数据里算出一组 P0–P3，
  而那组数与真实运行的审计结论长得一模一样，评审分不出来。
* 账本 / 审计 / 经验三个面板报 `applicable: false` 并说明原因。这不是
  「空」，是「不适用」：`nCalls == 0` 读起来是「这次没调用过模型」，
  `verdict == None` 读起来是「还没判定」—— 两句都不是实话。
* `/api/cases/<id>/raw/<artifact>` 一律 404。拿不出东西时不能拿别的东西顶。

`summary.integrityOk` / `replayOk` 对展示轨迹是 **`null` 而不是 `false`**。
`false` 是「校验没通过」，而一份手写轨迹从来没被校验过 —— 说它没通过是
凭空指控。

#### 重跑与改数据

```bash
# 重新生成展示轨迹（幂等）
python3 webapp/showcase/build_ankle_showcase.py

# 重新跑真实分析（幂等，会覆盖）
python3 webapp/build_demo_run.py \
    --dataset-csv webapp/runs/ankle_demo/dataset_ankle.csv \
    --out-dir webapp/runs/ankle_demo --tag ankle --cases 0
python3 -m webapp.backend.zh.prefetch --cases 0   # 否则中文是花的
```

`build_ankle_showcase.py` 里事件通过名字引用父事件，ID 按发出顺序生成；每帧 delta
锚定在完成该帧因果图更新或过程事件上。L2 核验与首轮 MRI 反证合并显示；Backtrack
步骤将 `focusNodeId` 从 L2 切换到 L1，并同时标出回溯起点。MRI 检查按
`PLAN → AGENT_CALL → TOOL_CALL → EVIDENCE_READ → ANALYSIS → GRAPH_UPDATE` 记录，
纯过程事件不再单独占用一帧。

**改完数据要跑对齐校验**，它会同时比落盘数据与接口两层：

```bash
python3 webapp/showcase/check_alignment.py
```

#### 两个新字段：`why` 与 `level`

参考项目把 `why` 与 `level` 直接存在**节点自身的 attrs** 上；我们的来源不同，
因为要跟真实运行共用一套协议：

| 字段 | 来源 | 为什么 |
|---|---|---|
| `why` | 假设：**置信度轨迹**（`GRAPH_UPDATE` 的 `candidates[].why` / `edit[].why`，`PLAN` 焦点的 `why` 补深挖节点）<br>证据 / 知识：`bindings[].why` | 它回答的是「为什么是这个数」，必须跟那个数一起随时间轴走，不能是节点上的静态字段。真实运行的 `edit[]` 本来就带 `why`（不是为 showcase 造的） |
| `level` | `bindings[].level` 优先，回落到 PLAN 焦点读数 | 层级是节点的固有属性、不随步变；**每个**假设都得有 —— 列式布局按 `H{level}` 分列，缺一个它就掉进 H1 那列 |

`why` 一个字段两个来源、轨迹优先；两处都没有时是 `null`（不是空串）——
信号与两条查体发现在参考里就没有理由，它们是患者给的、不是推出来的。

#### 步骤标题与解说：一条**显式**的手写覆盖通道

当前展示的步骤为输入初始化、L1 假设生成、最高分 L1 深挖、L2 假设核验、MRI 反证、
Backtrack、回到 L1 最高分节点继续深挖、替代假设和最终报告。标题与解说保存在
展示 delta 中，**不混进真实运行的生成逻辑** ——
那会让「这一步在讲什么」变成一半生成一半手写，读的人分不出哪句是事实、
哪句是编排。

所以它是一条显式的通道：delta 自带 `title` / `narrative` 时直接用，没有就
照旧从事件事实生成（`services/delta.py::_authored`）。**真实运行的 delta 里
没有这两个键**，行为完全不变 —— 有测试守着这一条（真实运行的每个 delta
`title` 必须为空，且仍须生成出非空解说）。

展示轨迹的界面本来就有琥珀色「展示轨迹 · 无审计产物」标记，读者知道这一页
是可编排的。

`build_demo_run.py` **不写进 `S5B_final_heldout/`**：开头就拦，out-dir 落在
封存块里直接退出。演示运行与 held-out 评估必须分开 —— 动过封存块的哈希，
S5B 的结论就不再成立。

#### 换成真实分析输入时要知道的两件事

**图的复杂度是输入的函数，不是展示层的。** 这条踩过一次：第一版的病例
输入写成了完整病历（`Case Information` 439 字符 + `Physical Examination`
435 字符、5 个独立发现、检查池里还有化验），于是第 0 步就抽出 **5 条**
初始证据，两位不相关的专家（`Laboratory_Physician` / `Pathologist`）也
各自检索出了证据 —— 终图 13 节点 / 24 边。参考项目的信息量是「一个机制 +
两条查体发现 + 两项影像」，照那个量级重写输入后降到 8 / 14。

所以换输入时要跟着调两处：`Diagnostic Tests` 里**不要放与场景无关的检查
类别**（有对应专家就会去检索、就会多出节点），病例文本里**不要罗列阴性
排他描述**（每一条都会被当成一条独立发现）。

`Diagnostic Tests` 是**检索池**不是提示 —— 主诊看到的是 `Case Information`
+ `Physical Examination`，检查结果要靠工具去查，所以 X 光阴性与 MRI 所见
都放在池子里。

#### 登记

`webapp/runs/index.jsonl` 是真实运行的注册表（一行一个运行）。里面的
`run_dir` 写**相对仓库根**的路径，读的时候补全（`config.live_runs`）——
绝对路径焊进一个跟着仓库走的文件，仓库一挪整份索引就失效，而那种失效
看起来像「病例丢了」，排查方向会完全跑偏。

**病例列表只在 `_Dispatch.available()` 一处拼**（`sources/__init__.py`）。
曾经 `config.all_cases` 与它各拼了一次，`case-ankle` 就在 `/api/cases` 里
出现了两条，其中一条是 catalogue 的原始形状、**没有 `kind`** —— 按 id
索引时后写的赢，赢的正好是没有 `kind` 的那条，界面上就再也认不出它是
展示轨迹了。

**演示病例用任务名登记**（`config.DEMO_CASE = "case-ankle"`）。不是审美
问题：`0` 是假值，任何一句 `if DEMO_CASE:` 都会静悄悄地失灵（`case-0`
真实存在，所以这条不是假想）。

### 手动启动

```bash
pip install -r webapp/backend/requirements.txt
python3 -m uvicorn webapp.backend.app:app --port 8000

cd webapp/frontend && npm install && npm run dev
```

> **改完前端代码后，先确认 dev server 真的在发新代码。** Vite 的 watcher 会
> 漏掉改动 —— 实测过一次：文件已经改了（`grep` 得到新内容），而
> `curl http://127.0.0.1:5173/src/...` 拿到的还是旧模块。此时**浏览器里跑的
> 是旧代码，所有验证都是假的**，而且没有任何报错提示。验证一行就够：
>
> ```bash
> curl -s "http://127.0.0.1:5173/src/components/graph/layout.ts" | grep -c 你刚加的标识符
> ```
>
> 为 0 就 `touch` 一下文件；`touch` 也不管用就重启 dev server。**排查任何前端
> 故障之前先做这一步** —— 否则会对着一个根本不在运行的版本调试。

> **改完 `components/graph/` 下的文件后，页面要 Cmd+Shift+R 硬刷新。**
> Vite 的热更新走 React Fast Refresh，而它会**保留组件状态** —— 而模拟的
> handle 恰好就存在一个 ref 里。于是热更新之后可能出现「新代码 + 旧模拟对象」：
> 新代码调一个旧对象上不存在的方法，抛在 `onNodeDragStop` 里，React Flow 的
> 拖拽收尾就此中断。表现是**一拖动节点就不对劲**，而代码本身没有任何问题 ——
> 这一条花了很久才定位，因为它只在「开着 dev server 连续改布局代码」时出现，
> 全新打开的页面永远复现不了。三个方法现在都用 `?.` 调用，最坏也只是少做
> 一步（节点回弹），但硬刷新仍然是干净的做法。

## 中文化

推理管线产出的是英文（那是模型的输出，是**事实**）。界面要全中文，但译文
属于**展示层** —— 所以这一层被单独隔离出来，改它不会动到任何判定。

优先级是刻意的，`zh/translator.py`：

| 输入 | 走哪条路 | 为什么 |
|---|---|---|
| 短语（≤3 个英文词） | **词典**（953 条） | 短语没有语序问题，而术语一致性在这里最重要 —— `retinal vein occlusion` 在全文里必须是同一个说法 |
| 句子 | **整句缓存**，退回词典 | 词典是逐词替换，中英语序不同，替换完是「无 临床实验室证据眼内炎症 被发现」这种每个词都对、整句读不通的产物 |
| 缓存也没有 | **显示英文原样** | 未翻译的英文一眼可见；编造的中文词看不出来。缺什么补什么 |

**覆盖率的两个坑，都踩过：**

一是**分母**。报告原先只扫 held-out 那一个目录，于是「覆盖 100%」说的是
**那一个目录** 100%，而界面上还能点开另外 10 个病例 —— 它们的中文缺口不在
任何一份报表里。现在分母由 `config.all_cases()` 推导（`prefetch.default_roots`）：
用户能点开的范围，就是报表统计的范围。

二是**判据**。两个分支的「已覆盖」含义本来就不同（短语看词典、句子看缓存），
用一条判据套两支必错其一。更隐蔽的是**译文合格判据**：这里一度用「汉字占比
≥ 25%」判断模型有没有真翻译，而医学文本天然夹大量拉丁串 —— 一条完全正确的
译文 `PR3-ANCA升高，MPO-ANCA阴性`（4/21 = 19% 汉字）会被判不合格，卡掉的
全是合格译文，它想挡的「原样退回」反而另有更准的判据。现在直接比
`residue()`：源文里该翻的英文词少了没有。

缓存由 `zh/prefetch.py` 一次性生成（把全部展示文本交模型整句翻译、落盘）：

```bash
python3 -m webapp.backend.zh.prefetch --report      # 只看覆盖率，不调模型
python3 -m webapp.backend.zh.prefetch               # 补齐缺的（可随时中断续跑）
python3 -m webapp.backend.zh.prefetch --cases 85    # 只做某个真实运行的病例
```

展示轨迹（`case-ankle`）**不需要预翻译**：它的文本本来就是中文写的，
不走英译中那条路。所以换演示病例时，要先想清楚它属于哪一类 ——
产物型病例漏了这一步，界面上是花的，而且不会报错。

运行时**只读缓存，不联网、结果恒定** —— 界面上的中文一旦会随刷新变化，
就没法作为演示材料。

协议里译文与英文原文**同时下发**（`label` / `labelEn`、`io.output` /
`io.outputEn`）：译文属于展示层，可以被打磨；原文属于事实，审计与
「这句话真的是模型写的吗」的核对必须看它。只发译文会让界面上的每一句话
都无法回溯。

## 视觉

节点是**圆**，按类型填充，标签折行放在圆下方。形状与配色体系对齐
`医疗溯因智能体/gos_repo/viz/story_template.html` —— 同一套 GoS 流水线的
展示层，两个项目用同一套色，评审在两处看到同一个绿色时应当理解为同一件事。

三种修饰各自承担一件事，互不抢：

| 修饰 | 位置 | 回答的问题 |
|---|---|---|
| 等级徽章（P0–P3） | 压在圆的左上 | 这个节点有多可信 |
| P3 红色虚线圈 | 圆周围 | 这是无来源断言，要跳出来 |
| 增量环脉冲 | 本步变动的节点 | 这一步它变了 |

**填充色 = 节点类型，不是证据等级。** 类型是「是什么」，一眼要能分辨；
等级用徽章与描边更合适 —— 让填充色同时承担两件事，两件都会读不清。

### 边：照参考项目，直线 + 裁到圆周

参考项目的边只有一条规则加三行几何，但整张图的观感由它决定：

```js
const EDGE_COLORS = { support: "#22c55e", refute: "#ef4444", refines: "#94a3b8" };
const EDGE_W      = { support: 2.4,    refute: 2.6,    refines: 1.8 };
x1 = s.x + ux * (R[s] + 4)   y1 = s.y + uy * (R[s] + 4)   // 起点从圆周往外推 4px
x2 = t.x - ux * (R[t] + 4)   y2 = t.y - uy * (R[t] + 4)
```
```css
.edge { stroke-width: 2.2; opacity: .85; }
```

这里是**逐条照抄**的（`edges/geometry.ts`）。先前用的是
`getSmoothStepPath`（直角折线）**加上三种箭头**，而且 Handle 挂在节点外接盒的
上下边缘 —— 那个盒子含了圆下方的标签，所以线是从**标签底下**出发的，还常常
扎进下面那个节点的圆里。三处都不是参考项目的做法。

**踩到一个 React Flow 的暗坑，值得单独记：** 把 Handle 挪到圆心**没用**。
`getHandlePosition` 里锚点是**按 `position` 吸附到外接盒的边**上的：

```js
case Position.Top:    return { x: x + width/2, y }               // 盒子顶边
case Position.Bottom: return { x: x + width/2, y: y + height }   // 盒子底边
```

它**完全无视 Handle 自己摆在哪**。所以边的端点必须自己算：用
`useInternalNode` 现取两个节点的真实几何（绝对位置 + 外接盒宽度），
于是图形中心 = `(x + w/2, y + 图形中心偏移)`。它订阅 store，节点一动就重算，
拖动时线跟着走。

两处细节：

- **菱形端点的裁剪随方向变。** 菱形是边长 `r*1.7` 的正方形转 45°，顶点朝上下
  左右：沿轴走到的是**顶点**（最远），沿对角线走到的是**边**（最近）。用一个
  常数糊弄，要么沿轴时线钻进菱形，要么沿对角线时留一大块空。正确量是
  `a / (|ux| + |uy|)`，其中 `a = r*1.7*√2/2`。
- **新边「画出来」**：参考项目是 `dasharray = 线段长; dashoffset = 线段长`
  再过渡到 0（620ms）。这里用同一组数值交给 CSS 动画，长度由组件按当前实际
  线段算，所以节点移动、线伸缩时动画长度也是对的。

**一处刻意放弃的东西：箭头。** 参考项目一条 marker 都没有，它靠颜色区分关系。
我们先前用「实线+箭头 / 虚线+平头 / 点线+空心箭头」三套线型编码三种逻辑动作，
理由是「颜色在投影偏色、转黑白、色觉差异下会失效」——那个理由本身没错，但
用户要求与参考项目一致，所以以颜色为准。**线型的可用性是主动放弃的，不是遗漏**；
真要找回，位置在 `RelationEdge.styleOf` 的 `dash` 上，一条线的事。

**圆心写置信度。** 假设节点的圆里显示当前读数（两位小数），下方一个变化
徽标；变化时圆闪一下（升绿降红）。详见下面「事实 3」。

**悬停看详情。** 鼠标停在节点上，跟着光标浮出一层信息：类型、完整标签、
英文原文、**置信度**（含等级、支持/反驳计数、相对上一步的变化）、
**来源匹配度**（有记录时给数并低于 0.35 标红，没有记录时给一句说明）、
创建事件、来源类与语义类。
形状对齐参考项目的 `#tooltip`（深色、`+14/+14` 偏移、`max-width: 340px`），
两处修正：参考项目只做横向夹取，光标靠下时浮层会溢出容器；这里横竖都夹。

浮层挂在**画布层**而不是节点组件里 —— React Flow 给每个节点套了一层带
`transform` 的容器，`.graph-pane` 又是 `overflow: hidden`，浮层挂在里面会被
两者一起裁掉：靠近画布边缘的节点，浮层缺一半。

### 标签重叠的真正原因

**不是布局排不下，是盒子算错了。**

`wrapLabel` 原本用一个「汉字算 2、其余算 1」的显示宽度，再乘 5.6px 换算成
像素。那个模型对中文准（实测比值 0.98），对拉丁则错得离谱 —— 比例字体的
字宽本来就随字符变化：

| 标签 | 预测 | 实测 | 比值 |
|---|---|---|---|
| 未发现眼内炎症的临床或实验室证据（纯中文） | 179.2px | 176.0px | 0.98 |
| `ABCDEFGHIJKLMN` | 78.4px | 101.5px | **1.30** |
| `WWWWWWWWWWWWWW` | 78.4px | 146.0px | **1.86** |
| `rec-case-85-0001` | 151.2px | 155.0px | 1.03 |

后果不是「看起来有点挤」：盒子按 78px 算、文本实际占 146px，于是它在 DOM 里
**重新折行成更多行**，而那些行 div 是固定 `height: 13px` 的 —— 多出来的行直接
画到下一个节点身上。

修法两条，缺一不可：
1. **按字符类别的实测字宽表**（中文 11.0 / 宽拉丁 9.6 / 大写 7.6 / 小写 6.2 /
   数字 6.4 / 窄 3.5 px），盒宽再加 3% 安全余量。
2. **标签 `white-space: nowrap`** —— 让「估窄了」这条路在结构上不可能发生：
   最坏只是横向溢出几个像素，不会长出新的行、不会改变盒子高度。

顺带纠正一个想当然：**dagre 不会把标签排重叠**，即使 `nodesep` 压到 0 也不会，
它是按完整的盒子（圆加标签）算间距的。所以「换成力导向来消重叠」这个前提本身
就是错的 —— 见下。

### 布局：活着的锚定力导向

**预热到冷再交出去。** 参考项目建完模拟只预演 12 帧就让画面动起来，我们不行：
外层的视口是按**建好那一刻**的坐标算的，12 帧之后 alpha 还有 0.7，模拟会接着自己
跑两秒 —— 图就在用户眼前飘出画布。实测（正是这一条暴露出来的）两张图都是空的，
37 个节点里 19 个在框外。所以这里跑到 `alpha < alphaMin` 为止：第一帧就是终态，
视口算得准，画面也不再自己动。**运动只剩一个来源，就是用户拖动。**

**模拟一直在跑，不是在 `useMemo` 里算完就冻住。** 这一条是整个交互手感的地基，
先前写错过一次：那时坐标在渲染期算完就冻结，于是拖动一个节点时**邻居纹丝不动**，
松手是**瞬移回原位**（清掉覆盖值，坐标又来自那次冻结的计算）。参考项目里
`forceSimulation` 是活着的（d3 自己的定时器在跑），拖动会重新加热 alpha、整张图
跟着响应。现在照做：`useForceGraph` 把活的模拟接到 React Flow 上，每个 tick
重建一次节点数组。

> **但「每帧重建节点对象」有个很贵的副作用，必须由 `initialWidth` /
> `initialHeight` 抵消。** React Flow 渲染节点时写的是
> `visibility: hasDimensions ? 'visible' : 'hidden'`，而 `hasDimensions` 读的是
> **内部节点**的 `measured` —— 那是在 `adoptUserNodes` 里重建的，且只从
> **我们交出去的那个对象**上读：
>
> ```js
> if (checkEquality && userNode === internalNode?.internals.userNode) { /* 复用，保留 measured */ }
> else { internalNode = { ...userNode, measured: { width: userNode.measured?.width, ... } } }
> ```
>
> 我们每帧都交出一个新对象（`{...n, position}`），于是每帧都走重建分支，
> `measured` 被重置成 `undefined`，**整张图的节点全部 `visibility: hidden`**。
> 模拟一冷就不再交出新数组，重建停止，节点在约 2 秒后自己回来 —— 正好是
> alpha 衰减到停的时间。用户报的就是这个：**「一拖节点就消失，等 2 秒出现」**。
>
> 而我们**本来就精确知道每个盒子多大**（`boxOf` 是布局、碰撞力、渲染共用的同一个
> 真源）。把它交出去，React Flow 不必先量再显示，也就永远不会因为重建对象而翻回隐藏。
>
> **这一个字段撑起两件事，而且两次才修完 —— 因为两处的判据不一样：**
>
> | 用到它的地方 | 判据 | 只给 `initialWidth` 时 |
> |---|---|---|
> | 节点可见性 | `measured?.width ?? width ?? initialWidth` | ✅ 能救 |
> | `parseHandles` | `!userNode.measured ? undefined : 上一次的 handleBounds` | ❌ 只认 `measured` |
>
> 第二行是**边整批消失**的根因：`measured` 缺失 → `handleBounds` 被清空 →
> 节点变成「未初始化」→ `getEdgePosition` 返回 null → `EdgeWrapper` 直接
> `return null`，**连元素都不生成**（不是画不出来）。所以先修好节点之后，
> 症状变成「拖动时节点都在、边全没了」，松手约 2 秒又一起回来。
> 两个字段现在都给：`initial*` 管首次测量前的内联尺寸，`measured` 是一直留着的那个。
>
> 这两个故障对**所有既有检查都是隐形的**：`getBoundingClientRect` 照常有值、
> `opacity` 是 1、`display` 是 block、节点数一个不少。只有
> `getComputedStyle(...).visibility`、**截图的像素**、以及**边的数量**看得见。
> `check-drag.mjs` 现在在**按住不放时连续采 12 次**，同时量「隐藏了几个节点」
> 与「还剩几条边」—— 单点采样会正好落在两次清空之间而漏掉。

**推理图的锚点是语义列，不是 dagre 的拓扑分层。** 这是后改的：锚定力导向本身
照搬参考项目没错，但**锚在哪**先前答错了。参考的种子来自
`story_player.layout_nodes`，按 `Signal / Evidence / H{level} / Knowledge`
分列；我们用的是 dagre 的拓扑分层，而拓扑分层与语义**不是一回事** ——
`E4 --support--> H2a` 会让 MRI 证据排进**假设那一列**，
`KB104 --support--> H1b` 会把知识节点排进证据列。图是对的，读起来是散的。

现在两图分开：推理图走 `layout.columnSeedsOf`（按 n.data.column 分列、列内固定
行距、各列关于同一水平中轴对齐），执行溯源图仍走 dagre 的拓扑分层 ——
它的分层语义就是时间顺序，拓扑是对的锚。

**列内位置是 `(列, 行号)` 的纯函数** —— 行距固定、起点固定、列宽也是常数，
都与「这一列有几个节点」无关。这一条是列式锚点相对 dagre 的全部好处，也是
个踩过的坑：先写成「按该列的实际高度居中、列宽取该列最宽的盒子」，于是
**同列里每加入一个节点，已有节点全部平移半个行距**，一个长标签的新节点入列
还会让它右边的列整体平移 —— 而时间轴每走一步都可能加节点，整张图于是每步
重排一次。`scripts/check-layout.ts` 盯住了这两条（去掉任一条，两条断言变红）。

代价是与参考项目的一处**有意偏离**：它把每列按实际行数均分到一条竖带上，
所以各列中点对齐；我们改成各列从同一个 y 起排。它能均分是因为它一次把整个
故事发给播放器、一开始就知道全帧节点，我们的接口是**按步取图**的，拿不到
未来。列内顺序因此从 `deltas[].addedNodes` 拼出全帧并集顺序传进来 ——
顺序本身不含标签与分数。

**与参考项目逐项对照后，只有三处偏离，每一处都是量出来的，不是审美：**

| | 参考项目 | 这里 | 为什么 |
|---|---|---|---|
| 连杆静止长度 | 常数 150 | **每条边取两端种子距离** | 150 是**它自己的种子间距**的度量。我们的种子是 dagre（ranksep 96/62），拿 150 要求一条本来 96 的边，等于每条边带一个 54px 的永久弹簧误差，且沿链累积：实测 13 节点被推散 587px。改成逐边种子距离后降到 29px，净空缺口从 11 对降到 0 |
| 分离力 | `forceCollide`（圆） | **轴对齐矩形，沿重叠较小的轴推开** | 参考的圆半径 `R + 6 + min(26, len*1.4)` 圆心在节点中心、而标签挂在圆**下方**，根本没把标签圈进去。补成「外接盒的外接圆」两个方向都不对：横向要求 132px（实际只需 80），斜向又**不够** —— 圆不重叠不保证矩形不重叠。实测按圆分离后 TB 图仍挤着 8 对 |
| 松手行为 | 清 fx/fy，缓缓回位（实测回弹 **94%**） | 锚点跟到落点 + 重铸该节点的边 | 用户明确要求「松手不回弹」。见下节 |

其余参数逐个照抄：`charge -320`、`linkStrength 0.5`、`alpha 0.7`、`alphaDecay 0.05`、
拖动时 `alphaTarget 0.25`。锚定强度仍是 0.3 / 0.12，但**按方向取** ——
参考项目里 0.3 永远给 x，因为它的种子是竖着的列；我们的分层轴在 TB 图上是 y，
照抄常数值会把弱锚定放在分层轴上，正好反了。

**分离力必须注册在最后。** d3 按注册顺序逐个调用 force，而锚定力每帧都会把节点
拽回种子位置 —— 排在前面的分离刚把盒子推开，后面的锚定又推了回去。实测 TB 图
因此留下 17 对压在净空里的盒子。排在最后，它就是每帧最后一个写坐标的人。

```
node scripts/check-layout.ts       # 零重叠 / settle 的确定性 / 净空 / 形变有界 / 拖动语义
node scripts/check-rendered.mjs <url>   # 量浏览器里真正渲染出来的盒子
node scripts/check-drag.mjs [url]       # 真浏览器里真拖，量连带与回弹
```

第一个脚本验的是布局**数学**，第二个验的是**算出来的盒子和浏览器画出来的一致**
（上面那个「预测 78 vs 实测 146」的错误在布局数学里完全正确，只有量渲染结果才
看得见），第三个验的是**截图看不出来的那两件事** —— 邻居有没有跟着动、松手有没有
弹回去。

> 第一个脚本里「两次运行逐位相同」这条**只对 `settle()` 成立**：它每次从 dagre
> 种子出发同步跑到冷，是输入的纯函数。界面用的是活着的模拟，坐标从上一帧继承，
> 是**路径相关**的（从第 1 步走到第 5 步，与直接跳到第 5 步，落点可能不同）。
> 这一点我们**照搬了参考项目**，不再声称是改进。

**标签始终显示。** 这里原本有一个「低于 0.52 倍不画标签」的阈值，理由是
「11px 的字缩到 0.42 是噪点」。那个理由在当时是对的 —— 因为当时标签会互相
重叠，缩小之后一片糊。重叠的根因修掉之后，缩小只是变小，不再是噪点；留一个
阈值反而让整图视图变成「一片没有文字的圆圈」。现在可读性由排版保证，不再由
「藏起来」保证。

**节点可自由拖动，松手**即定住**。** 与参考项目**刻意不同**的一处，这里是判据：
先按参考实现做了一版，实测**参考项目自己也回弹** —— 用真浏览器拖它的真实播放页，
拖 192px 松手后回到离原位置 11px 处，即回弹 94%。所以「严格照参考」与「松手不回弹」
不能同时成立，按用户的选择取了后者。

做法两步，缺一不可（都写在 `layout.ts` 的 `reanchor` 里）：

1. **锚点跟到落点。** 锚定力是 `(sx - x) * strength`，把 `sx/sy` 设为当前位置，
   锚定力恰好为零。
2. **把该节点连出去的每一条边按当前几何重铸成新的静止长度。** 边的静止长度是
   初始化时按种子算好存下的，节点被拖走 300px 之后那几条边全都绷着三百多像素，
   松手时合力把它拽回去。只重铸这**一圈**边，不动图里其它边 —— 全局重铸会把
   整张图的平衡态一起改掉。

两步各自的效果是量出来的：都不做回弹 94%，只做第一步 61%，两步都做 **25%**
（推理图）/ **20%**（溯源图）—— 剩下的那些是邻居松弛回原位时带的一点回拖，
正是「其余节点慢慢松弛过去」应有的样子。

> 顺带记一个 d3 的坑，它让第一步**静默失效**了很久：`forceX` / `forceY` 在
> `initialize()` 里就把目标坐标算好塞进内部数组（`xz[i] = +x(node)`），之后
> 每帧只读那个数组，**不再调用访问器**。所以光改 `sx/sy` 是彻底无声的 ——
> 实测四种改法结果逐位相同。改完必须 `force.initialize(nodes)` 重新初始化。
> `forceLink` 把静止长度同样缓存成 `distances[i]`，同理。

**但「定住」必须配一个拖动上限，否则它会自己把自己拆掉。** 节点要停在被放下的
地方，连接它的边就不能绷着 —— 于是只能把邻居一起拽走。也就是说「定住」**必然
永久改变布局**，改动量正比于拖多远。实测过一次没有上限的版本：拖动 770px
（比整张图 366px 还宽）之后，图的流坐标包围盒从 366×1149 涨到 **1463×1239**，
一多半节点被推出画布，而且反复拖会持续累积。所以落点被夹在**离原始种子
200px** 的圆内（`REF.maxPull`）—— 足够把压在一起的标签挪开（拖动本来的用途），
又不足以把分层结构拆掉；相对**原始**种子量，反复拖也不累积。

**还有一条 React Flow 的默认行为必须关掉：`autoPanOnNodeDrag`。** 它的用途是
「你把节点拖到画布边缘时自动平移，好让你拖到视野外」。而我们的节点被上面那个
半径钉住了 —— **节点先停住、光标继续走**，于是它判定「用户想拖出去」，开始一路
平移画布。实测：节点流坐标只挪了 ~130px 就停住，而视口从 `translate(194px)`
一路跑到 `translate(-436px)`，**整张图被推出画布**。这就是用户报的
「一拖节点就消失」，而且它躲过了所有既有检查 —— 被拖的那个节点**全程都好好地
跟着光标**，跑掉的是别的节点。两张图都设了 `autoPanOnNodeDrag={false}`，
由 `check-drag.mjs` 的「远拖之后镜头跑不跑」钉住（分开量「视口有没有动」与
「图还在不在」，因为两者的修法完全不同）。

代价说清楚：**分层语义因此可以被用户改掉**。拖走一个节点，它就留在那儿，
「证据→假设→结论」的阅读顺序会被局部破坏，而读者分不出自己看到的是不是原图。
这是为了「挪开看一眼被压住的东西」付出的代价，切换步骤会重新播种、恢复分层。

**两张图都按步长出来。** 这里曾经只有左图在长：`/provenance-graph` 一次性
给出全部 37 个节点，于是时间轴还停在第 1 步，右边的执行图已经是完整终态 ——
等于把「协作过程」直接跳过去只留结果，而这张图存在的全部理由就是过程。更糟的
是它与左图不对称，右图会被读成一张静态背景。

现在两张图都接受 `?step=N`，右图逐步长出来：**2 → 3 → 26 → 36 → 37** 个节点。
裁法是：事件节点按事件日志的序号裁；Agent / Tool / Record 没有自己的序号，
随**第一个引用它们的动作**出现。由 `test_provenance_graph_grows_with_the_timeline`
钉住，其中两条不变式是关键：每一步都不能有悬空边、**回放到最后一步必须与
不回放逐字段相同**（它们是同一次计算的不同时刻，不一致就说明有一处在撒谎）。

**镜头跟着当前步骤走。** 两张图的默认视图都是「装下整张图」；溯源图有焦点
（用户选中的事件，没有选中时是**本步的图更新事件**），此时镜头以焦点为中心，
并按它的一跳邻域决定**拉多远**。

这里改过两次，两次的错法正好相反，值得记下来：

- 先是「框住焦点的一跳邻域」。执行图按时间纵排，一个事件的上下游可以横跨
  十几个 rank，包围盒比画布高得多 —— 适配要么被缩放下限截住（内容溢出、
  顶端节点被削掉一半），要么缩到 0.2 倍。
- 改成纯「对准焦点」之后不裁了，但画布大半空着，看不见邻居。

正确的问法是：**以焦点为中心**，要拉到多远才能把邻居也收进来。中心是确定的
（焦点在哪不是数据的偶然），距离按内容算。

**但「按内容算」这一步也算错过。** 这里一度是按**邻域包围盒**算倍率的 ——
那是「视图对准包围盒中心」时才对的做法，而这里明确是**对准焦点**的。焦点通常
落在包围盒的边上，于是包围盒朝另一侧伸出去两倍，那一侧的邻居全被挤出画布：
节点没丢，是镜头没框住它们。实测选中一个 9 度的节点只有 **6/15** 个可见，
用户看到的就是「图消失了大半」。正确的量是**焦点到每个成员最远边缘的距离**：
视图半宽必须装得下它。改完 6/15 → **15/15**，溯源图同步从 19/37 → 25/37。

由 `node scripts/check-drag.mjs` 的最后一段钉住（「选中之后整张图还在吗」）——
它量的是**画布内还剩几个节点**，因为这类故障在 DOM 里完全看不出来：节点都在、
无异常、无 NaN。

**推理图同理**：选中一个节点时**对准**它，并按它的一跳邻域决定**拉多远** ——
两处现在写法一致。

> 这里踩过一个很贵的坑：推理图原先写的是「**不要**邻域，0.95 倍怼近」，
> 理由是「邻域包围盒可能横跨整张图，适配出来要么被截住要么缩到读不清」。
> 那个理由是**错位的** —— 它讲的是「框住邻域」，而 `fitIds` 只决定**拉多远**，
> 中心始终是焦点，还有 0.3 的地板。错位一直没暴露，是因为那个视口 effect
> 当时**从来没有执行过**（依赖 `nodes` 被每帧推迟，见上文）。effect 一修好，
> 0.95 第一次真的生效 —— 而我们的图比参考项目大得多，0.95 倍下画布里**只剩
> 被选中的那一个节点**。任何一次点击（拖动收尾也常常算点击）看起来都像
> 「整张图消失了」。实测：修之前点一个节点后可见 1/15，修之后 10~14/15。

### 数据流

```
封存 artifact ──> sources/artifact.Bundle ──> services/* ──> schemas ──> HTTP
                        │
                        └─ 同一套读取代码
                        │
真实分析产生的运行 ──────┘   （第二阶段：结构完全一致，前端无感）
```

**演示模式与真实分析模式共用完全相同的可视化协议。** 这不是一句约定：
`sources/base.py` 定义 `ArtifactBundle`，两种来源都交出同样的东西，
上层走同一条代码路径，前端代码里不出现任何病例号 —— 病例号来自 URL，
演示病例由后端的 `config.DEMO_CASE` 决定并通过 `/api/cases` 的
`isDemo` 标记下发。

第三个数据源（手写展示轨迹）是照着第一阶段留的接口加进来的，`services/`
里一行没改 —— 那是「上层代码不需要改」那句话的兑现。唯一的例外是审计层：
它读 `bundle.kind` 决定**不跑**，因为「跑不跑审计」本身就是这第三类数据
的定义性区别，不是实现细节。

数据源由病例号分发（`sources/__init__.py` 的 `_Dispatch`）。**病例列表也
只在那里拼一次** —— `config.all_cases()` 只管产物型病例，展示轨迹由
`showcase.case_refs()` 加。两边各加一次会让同一个 id 出现两条、形状还不
一样，而按 id 索引时后写的赢。

### 三条硬约束（都在类型层面表达）

1. **算法判断只由后端产生。** `tier` / `anomaly` / `outcome` / `gate`
   四类字段在前端类型定义里全部 `readonly`，没有本地推导路径。一旦前端
   能自己算 tier，界面上就存在两个可能不一致的 tier 来源。

2. **中文业务文案不在前端硬编码。** 每个枚举值成对下发（`tier` +
   `tierLabel`），词表真源是 `i18n.py`。前端查不到会渲染成空白，而空白
   是看不出来的错。

3. **展示层只读事件与图快照，不修改诊断状态。** 推理/溯源运行时负责生成
   因果图和事件 DAG；工作台从这些产物构建逐步回放视图。审计与门控继续复用
   `audit_task` / `detect_task` / `experience_gate` / `memory_formatter`。

## 五个已核实的事实，与它们各自决定的设计

这些不是背景说明，每一条都直接决定了一处实现；改动它们之前请先读这里。

**1. 因果关系与事件依赖分开保存。**
`refines`、`support`、`refute` 属于因果图；`_provenance_graph.json` 是事件 DAG，
只用无类型的 `src` / `dst` 边记录父事件到子事件的依赖。
⇒ 推理图**必须**从 delta 重建，不能从事件 DAG 推断因果边；由
`test_refines_edges_exist_only_in_deltas` 钉住。

**2. 双图关联由事件节点显式引用。**
每个事件节点的 `causalNodeRefs` 保存它关联的因果图节点 ID；依赖边只连接事件。
检索原文保存在 `TOOL_CALL` 的 payload 中。历史版合并图仍由读取层兼容；新产物
不再构造 Agent / Tool / Record 等额外图节点，也不在事件边中混入因果边。

**3. 置信度是逐步重建出来的，不是节点的固有属性。**
（**这一条写错过两次，两次的错法都留在这里，因为错法本身有信息量。**）

- 第一版：「GoS 的节点置信度从不落盘，四个 artifact 里 `score`/`conf` 出现
  次数均为 0」⇒「界面不显示置信度」。**错的** —— 当时只在 `bindings` /
  `_provenance_graph` / `_deltas` 三类产物里找过，没往 `events.jsonl` 里找。
- 第二版：「落盘在 PLAN 事件的 `payload.focus` 里」⇒ 按焦点读数显示。
  **位置对了一个，但那只覆盖 28% 的假设。**

真实形状是**每步都有**。主来源是 `GRAPH_UPDATE` 事件的响应，三个位置：

| phase | 字段 | 含义 |
|---|---|---|
| `ingest:l1_hypo` | `candidates[].confidence` | 初始假设建立时的分数 |
| `update_graph` | `nodes[].confidence` | 本轮新建假设的分数 |
| `update_graph` | `edit[].confidence` | 本轮对既有假设的重新评估 |

按步累积起来就是每个假设的**读数轨迹**。加上 PLAN 焦点读数（补深挖节点的
空位，见下），覆盖从 28% 提到 **92%**（298/325 个假设），其中 77% 有 ≥2 个
读数，也就是能显示变化量。

**响应里的节点用的是局部 id（`h001`/`ev001`），图上用的是 `node-5`，两者
只能靠 label 对上。** 局部 id 还不能跨步复用 —— case-85 里 `ev001` 在第 1 步
是 `node-8`、第 2 步是 `node-14`，拿它当键会串行。实测 40 个病例 441 条读数
零次撞名（撞名时整个丢弃，映射到错的节点比不映射更坏）。

**深挖是第二个来源，而且它只记了一半。** `run()` 里主诊决定不交卷时，会按
`candidates` 直接建一批 L+1 的假设并带上 `confidence` —— 这条路不经过
`update_graph`，落盘的 `DRILL_DOWN` 事件里**只记标签、不记分数**。那批假设
的分数只出现在一个地方：它被选为规划焦点时的那行读数。所以轨迹是两处的
**并集**，PLAN 只补空位。

两处都记了的时候它们**相等** —— 114 条焦点读数逐条核对，93 条两处独立一致、
21 条是深挖节点（轨迹里本就没有）、**0 条矛盾**。这是这套重建唯一的外部检验：
PLAN 读数是运行当时规划器真正看到的值，与从响应重放出来的是两条独立落盘路径。

**它不是参考项目那套公式算出来的数。** 参考项目的 `gos_repo` 有一层置信度
工程化（`belief/confidence.py`，文档 3.2.5）：

```
z_t(h) = z_{t-1}(h) + Σ r_e·d_e·q(e,h)        有证据边时累积（r_e = 0.12）
z_t(h) = z_{t-1}(h) + α·(q_target − z_{t-1})   无证据边时温和收敛（α = 0.35）
再对同层假设做 min-max 归一化到 [0.05, 0.95]
```

**本仓库冻结的 `gos/` 把这一段整个移除了** —— `gos/belief/` 下没有
`confidence.py`，`configs/Belief_Configs.yaml` 里也没有 `confidence:` 段，
`central_agent` 里直接 `score = LLM 返回值`。这正是参考项目文档里写的
`enabled: false`（LLM 直出）消融档。

两边数必然不同，而且差异可复算：case-85 的 `node-5` 那一步拿到 5 条支持边，
套公式是 `0.75 + 0.12×5 = 1.35 → 截断 0.95`，而归一的读数就是运行自己记下的
**0.85**。审计工具必须显示运行实际产生的那个数 —— 显示一个从未发生过的值，
正是本系统要防的事。

**显示形状**（对齐参考项目）：假设节点的**圆心直接写分数**（两位小数），
下方跟一个变化徽标 `▲ +0.10`（升绿 `#16a34a` / 降红 `#dc2626`，只在真的
变了时出现）。**与参考项目的一处有意差别**：它把 Δ 摆在圆**外面**下方
（`dy 36`），我们摆在圆内 —— 圆外只隔 5px 就是标签（`LABEL_GAP`），而节点
外接盒高度是布局与分离力共用的，让 Δ 参与布局会使盒高随步骤变化，时间轴
一 scrubbing 整张图就抖。

**节点类型与尺寸照抄参考项目**（`story_template.html` 的 `NODE_COLORS` /
`NODE_R`）：Signal `#ef4444` r34、Evidence `#22c55e` r26、Hypothesis
`#f97316` r28、Knowledge `#8b5cf6` r22 **紫菱形**。知识节点的菱形是形状本身
在说话 —— 它不是一条证据，是一条知识。（半径差 4px 看不出来，但那不是
「算了」的理由：评审会并排比。）

两处按我们的需要保留的差别：非假设节点仍显示类型字母（参考项目把它们
的角标 `fill` 设成 `transparent`，等于不显示）；层号 `L1/L2` 放在浮层表头
（`诊断假设 [L1]`，与参考的表头同形），不占圆上方的位置（那里已经是
P0–P3 等级徽章）。

**知识边单独一色**（`#8b5cf6`）：`KB104 --support--> H1b` 与
`E1 --support--> H1b` 关系同是 support，但一条是本次诊疗查出来的、一条是从
库里取的。不区分的话，读者会以为支持边都来自检查。图例里也单列「知识支持」。
它**从源节点的类型推**，不新增协议字段 —— 参考的 `isKbEdge` 也是这么做的。

**变化量相对「上一步」算**，与参考项目的角标同义（它拿 `prevNodes` 比，
那就是上一帧）。一个节点这一步没被重新评估 → 变化量是 **0（持平）**；
它这一步才出现 → **null（没有可比的前值）**。「没动」和「不知道动了多少」
是两件事，不要合并。

⇒ **「暂无读数」与「读数是 0」必须分开**。前者显示「暂无读数」，后者才是
0.00。混用会让「没测过」看起来像「测出来是零」。剩下 8% 没有读数的假设，
全部是**深挖产生但从未成为焦点**的候选（case-104 的 `node-14/15/16`）。

case-85 里 node-5 是 `0.75 → 0.85`，而上调那一步（`step 2`）**紧跟**在
「新增 P3 无来源断言并对 node-5 建立支持边」之后。**一条审计判为无来源的
断言，把信念推高了 0.10。** 这是本系统论点的最小证据。

**「支持 8 · 反驳 0」是从回放的图里数出来的**，不是读焦点读数 —— 定义与
参考项目 `BeliefFSM._count_support_edges` 一致（按**目标**节点数）。它与
焦点读数逐条核对过 **114/114 精确一致**，所以可以给每个假设都算，而不只是
当过焦点的那些。非假设节点不显示这一行：对一条证据说「支持 0 · 反驳 0」是
把「不适用」说成了「零」。

实现见 `services/belief.py`；由 `test_belief_readings_are_absent_before_they_happen`
钉住「读数不能提前泄露未来」（现在测的是一条完整轨迹 `无 → 0.6 → 0.65 → 0.65`
与它每一步的 Δ）。

**来源匹配度是另一回事**（`match_coverage`，持久化在 `bindings.json`）。
它只在**绑定了检索记录**时才有意义 —— 全库 599 条取值为 0.0 的，绝大多数
不是「匹配度低」而是压根没有可比对的东西：

| `match_tier` | 有记录 | 语义 | 显示 |
|---|---|---|---|
| `input` | ✗ | 证据来自病例输入 | 「来自病例输入，无检索可比对」 |
| `n/a` | ✗ | Signal / Hypothesis，本就不比对 | 「该类型不与检索记录比对」 |
| `none` | ✗ | 检索过，但没有记录被绑定 | 「检索过，但无记录被绑定」 |
| `none` / `paraphrase` | ✓ | 绑定了记录 | **数值**，与 0.35 阈值比 |

对起始信号显示 `0.00` 是在回答一个没人问的问题，而读者会把它读成
「匹配得很差」。case-85 里四个有数值的节点正好演示了阈值的意义：
`node-8 = 1.00`、`node-9 = 0.88`、`node-10 = 0.20`、`node-14 = 0.25`，
而审计的 tier 依次是 P0 / P0 / P2 / **P3** —— 0.35 那条线就在 0.25 与
0.88 之间。

注意区分：`AnomalyPath.confidence`（0.8）是**异常检测器**的置信度，
与规划器的信念读数也是两回事。

**4. id 体系有两套。**
delta 用裸 `node-N`，溯源图用带前缀的 `gos:node-N` / `evt-…` / `rec-…`。
⇒ 规范化统一向带前缀的一侧对齐（`reasoning_graph.norm_node`）。混用会让
「点节点高亮事件」**静默失配** —— 不报错，只是高亮错的那一步。

**5. 运行期绑定与审计判定可能不一致 —— 这正是本系统的论点。**
node-14 在运行期被绑定器绑定到 `rec-case-85-0001`（`match_coverage` 0.25），
合并图里因此有一条 `SUPPORT(Record→Evidence)` 边；审计按 0.35 的软匹配阈值
判定 0.25 不够，于是它是 **P3 无来源断言**。
也就是说：**图上有「支撑」的边，审计说那条边撑不住。** 只看推理图会看到一条
支持关系，只有把审计叠上去才知道它不成立。
由 `test_runtime_binding_claims_support_that_audit_rejects` 钉住 ——
如果哪天两者被「对齐」了，这个系统就失去了它的论点。

## 关键设计取舍

**为什么用 delta 重建而不是读溯源图** —— 见上文事实 1。副产品是每一步的图
状态都是免费的：时间轴回放与最终图走同一条代码路径，因此「回放到最后一步」
与「最终图」**不可能**不一致。

**为什么前端显示错误用「压暗」而不是「隐藏」** —— 隐藏会让图在点击瞬间
少掉一半，看的人失去空间参照。「仅显示关联路径」是用户显式要求的例外。

**为什么时间轴按步向后端取图** —— 多一次请求换来的是：界面上出现的图
**必然**是那一步真实的图，而不是前端自己从增量算出的近似。后者一旦与后端
重建逻辑有出入，演示就变成了自证。

**为什么账本里的「未提交」用暖黄而不是红** —— 检索阶段的调用本来就不提交到
任何图元素（设计如此）。把 9 条这样的调用涂成警示色，会把正常流程显示成一片
异常。

**为什么隐私边界的检查结果显示「无法验证」而不是打勾** —— 参考答案在本部署中
不可读（只存 sha256），所以「经验卡不含参考答案」这句话**无法被完整验证**。
界面必须这么说，而不是打一个它验证不了的勾。能验证的两项（患者原文、系统自身
预测）确实逐项比对了。

**为什么视口是自己算的，不用 React Flow 的 `fitView({nodes})`** ——
它内部走一条异步队列（`fitViewQueued` → `nodeQueue` → `requestAnimationFrame`
→ `setNodes`），触发链上任何一环不落地，返回的 Promise 就永远不 resolve，
而视口纹丝不动、不报错、查无可查。实测在无头浏览器里就是这样。而「聚焦到这几个
节点」需要的一切本来就在手上：dagre 已经算出了位置，`nodeBox` 算出了尺寸，
容器尺寸从 React Flow 自己的 store 读。自己算一次加减乘除要可靠得多，也能单测。

**为什么推理图后来也改成自己算（它原先用 `fitView`）** —— `fitView({minZoom: 0.6})`
的语义是「适配，但别缩到 0.6 以下」。图一旦装不进 0.6 倍，它就**停止缩小**，
内容溢出画布被裁掉：截图里顶部的起始信号只剩半个圆，底部一排证据节点齐刷刷断在
边缘，看起来像是布局算错了，实际上是「装不下」被呈现成了「被裁掉」。正确的分工是
**两件事分开**：适配的下限要低到总能装下（0.2），而**不要**给它加上限去「保证
可读性」—— 上限只会让内容被裁掉。可读性现在由排版保证（盒子算准 + 分离力给净空
+ 标签 `nowrap`），不再由「缩太小就把标签藏起来」保证，所以标签**始终显示**。
同一个坑在溯源图上又踩了一次（这次的受害者是「框住焦点的邻域」），两处现在共用
`focusViewport` / `centerOn`。

**为什么是 `centerOn` 而不是「框住邻居」** —— 见上文「镜头跟着当前步骤走」。
一句话：包围盒的大小由邻居决定，而邻居的分布是数据的偶然；焦点在哪儿是确定的
问题，就该由确定的东西回答。

**为什么下边栏默认收起** —— 它常驻 264px，把两张图压掉近三分之一高度，而演示
最该看的就是图。收起后它只剩一行：三个标签 + 三个操作按钮 + 展开按钮。操作条
（仅显示关联路径 / 定位来源 / 查看证据）原本是独立的一行，并进这里是因为它操作
的正是图 —— 收起来会让它无处安放。点标签即展开，点已展开的同一个标签即收起。

**为什么「当前步骤详情」从下边栏挪进了左栏** —— 它回答的是「这一步/这个节点
是怎么回事」，与它上面的叙事是同一个问题的两段答案，分在两处反而要来回看。
挪过去之后下边栏只剩三块可以慢慢翻的东西（审计 / 账本 / 结算），而它们是
**查阅**而不是**跟随播放**，正好适合收起来。

**为什么画布外层不能用 `height: 100%`** —— `.graph-pane` 的高度由内容决定，
子元素的 `100%` 于是指向一个 auto 高度，两者循环依赖、塌缩成 0（实测 190×0）。
用绝对定位对齐已定位的父级，绕开这个循环。

## 已知限制

- **前端产物 577 kB（gzip 188 kB）未做代码分割**，主要是 React Flow。本地
  演示工具，不值得为此增加构建复杂度。
- **`/reasoning-graph?step=N` 每次回放都请求一次后端**（前端有缓存）。本地
  往返 ~5 ms，播放间隔 1.7 s，无感。
- **真实分析模式的耗时为分钟级**（S5B 实测中位数 400 秒/例），前端需要明确的
  阶段进度与断线重连 —— 这是第二阶段的主要设计工作量。
- **`_provenance_graph.json` 缺失时从事件重建执行图**这条路径尚无真实数据
  覆盖（需要正在运行中的病例才能触发）。
- **自动适配的时机比直觉晚**：视口是「图到了」之后再加 120 ms 才算的，而连按
  时间轴时每次都会发一个取图请求，最后一次可能两三秒才回来。实测连按 3 次时
  第 4 步的适配发生在按完 4 秒之后。截图脚本因此把等待从 1800 ms 提到 4500 ms
  —— 1800 ms 拍到的是「节点已在图上、镜头还没跟过去」，看起来像节点跑到了
  画布外，但那是**拍照太早**，不是应用的问题。
